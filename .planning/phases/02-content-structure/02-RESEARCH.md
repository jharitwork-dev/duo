## Summary

Phase 2 builds the core teacher content-creation workflow and student navigation. The database schema is already deployed from Phase 1 but is **missing several columns** required by the CONTEXT.md decisions: `inviteCode` on classrooms, `maxGroupSize` on classrooms, soft-delete fields on phases and todos, and a templates table. These schema additions must be the first task before any CRUD work begins.

The UI pattern is a vertical collapsible outline with inline add/edit and drag-and-drop reorder for phases and to-dos. The new `@dnd-kit/react` v0.5 package provides a clean React API for sortable lists. All mutations should follow the existing Server Actions pattern in `src/server/actions/`. The project uses Next.js 16 with App Router, so route groups, Server Components for data fetching, and `'use server'` actions are the established patterns.

**Primary recommendation:** Start with schema migration (add missing columns + templates table), then build Server Actions layer for all CRUD, then build UI pages top-down (classroom list -> classroom detail -> group page with phases/todos -> todo detail).

### Pattern 1: Server Action with Zod Validation
**What:** Every mutation is a Server Action that validates input with Zod, checks role with requireRole(), and returns a typed result.
**When to use:** All CRUD operations (create classroom, add student, create phase, etc.)
**Example:**
```typescript
// src/server/actions/classroom.ts
'use server';

import { z } from 'zod';
import { db } from '@/db';
import { classrooms, classroomMembers } from '@/db/schema/classrooms';
import { requireRole, getCurrentUserId } from '@/lib/auth';
import { ROLES } from '@/lib/constants';
import { createId } from '@/lib/ids';
import { eq } from 'drizzle-orm';

const createClassroomSchema = z.object({
  name: z.string().min(1).max(100),
  description: z.string().max(500).optional(),
});

export async function createClassroom(input: z.input<typeof createClassroomSchema>) {
  await requireRole(ROLES.TEACHER, ROLES.SUPERADMIN);
  const userId = await getCurrentUserId();
  const data = createClassroomSchema.parse(input);

  const inviteCode = generateInviteCode(); // 6-char alphanumeric

  const [classroom] = await db.insert(classrooms).values({
    name: data.name,
    description: data.description ?? null,
    createdBy: userId,
    inviteCode,
  }).returning();

  // Auto-add creator as teacher member
  await db.insert(classroomMembers).values({
    classroomId: classroom.id,
    userId,
    role: 'teacher',
  });

  return { success: true, classroomId: classroom.id };
}
```

### Pattern 3: Invite Code Generation
**What:** Generate 6-character uppercase alphanumeric codes, check uniqueness.
**When to use:** Classroom creation (D-01) and code regeneration (D-02).
```typescript
// src/lib/invite-code.ts
import { db } from '@/db';
import { classrooms } from '@/db/schema/classrooms';
import { eq } from 'drizzle-orm';

const CHARS = 'ABCDEFGHJKLMNPQRSTUVWXYZ23456789'; // No I/O/0/1 to avoid confusion

export function generateCode(length = 6): string {
  const arr = new Uint8Array(length);
  crypto.getRandomValues(arr);
  return Array.from(arr, (b) => CHARS[b % CHARS.length]).join('');
}

export async function generateUniqueInviteCode(): Promise<string> {
  for (let i = 0; i < 10; i++) {
    const code = generateCode();
    const existing = await db.query.classrooms.findFirst({
      where: eq(classrooms.inviteCode, code),
    });
    if (!existing) return code;
  }
  throw new Error('Failed to generate unique invite code');
}
```

### Pattern 4: Soft Delete
**What:** Archived flag instead of hard delete. Queries filter out archived items by default.
**When to use:** Phases and to-dos (D-14).
```typescript
// In queries, always filter:
const activePhases = await db.query.phases.findMany({
  where: and(eq(phases.groupId, groupId), eq(phases.isArchived, false)),
  orderBy: [asc(phases.orderIndex)],
  with: { todos: { where: eq(todos.isArchived, false) } },
});

// Soft delete action:
export async function archivePhase(phaseId: string) {
  await requireRole(ROLES.TEACHER, ROLES.SUPERADMIN);
  await db.update(phases).set({ isArchived: true, updatedAt: new Date() }).where(eq(phases.id, phaseId));
}

// Restore action:
export async function restorePhase(phaseId: string) {
  await requireRole(ROLES.TEACHER, ROLES.SUPERADMIN);
  await db.update(phases).set({ isArchived: false, updatedAt: new Date() }).where(eq(phases.id, phaseId));
}
```

### Pattern 5: Drag-and-Drop Reorder with @dnd-kit/react 0.5
**What:** Sortable list using the new @dnd-kit/react API.
**When to use:** Phase reordering (D-08), to-do reordering within phases.
```typescript
'use client';

import { DragDropProvider } from '@dnd-kit/react';
import { useSortable } from '@dnd-kit/react/sortable';
import { move } from '@dnd-kit/helpers';

function SortablePhase({ phase, index }: { phase: Phase; index: number }) {
  const { ref, isDragging } = useSortable({
    id: phase.id,
    index,
  });
  return (
    <div ref={ref} style={{ opacity: isDragging ? 0.5 : 1 }}>
      {/* Phase content */}
    </div>
  );
}

function PhaseList({ initialPhases }: { initialPhases: Phase[] }) {
  const [phases, setPhases] = useState(initialPhases);

  return (
    <DragDropProvider
      onDragEnd={(event) => {
        const { source, target } = event.operation;
        if (source && target) {
          setPhases((current) => move(current, source, target));
          // Persist new order to server
          reorderPhases(phases.map((p, i) => ({ id: p.id, orderIndex: i })));
        }
      }}
    >
      {phases.map((phase, index) => (
        <SortablePhase key={phase.id} phase={phase} index={index} />
      ))}
    </DragDropProvider>
  );
}
```

**What:** Templates stored as JSON structure, not normalized tables.

### Anti-Patterns to Avoid
- **Client-side data fetching for initial loads:** Use Server Components to fetch classroom/group data. Only use client-side fetching for mutations and optimistic updates.
- **Storing templates as separate normalized tables:** Over-engineering. A JSON column is simpler for template structures that are applied once and then become independent records.
- **Hard-coding invite link domain:** Use an environment variable or derive from `process.env.NEXT_PUBLIC_APP_URL` for the invite link domain.
- **Nesting DragDropProvider:** Use a single DragDropProvider per page. Phase reorder and todo reorder within a phase can coexist under one provider if items have distinct types/groups.

## Common Pitfalls

### Pitfall 1: Race Conditions in Order Index Updates
**What goes wrong:** Two concurrent reorder operations produce inconsistent orderIndex values.
**Why it happens:** Optimistic UI updates fire before server confirms; two quick drags can conflict.
**How to avoid:** Use a transaction for reorder operations. Send the full ordered list of IDs to the server action, not just "move X to position Y". Server overwrites all orderIndex values atomically.
**Warning signs:** Items jumping positions after page refresh.

### Pitfall 2: Missing Auth Checks on Student-Facing Queries
**What goes wrong:** Students can see classrooms/groups they don't belong to by guessing URLs.
**Why it happens:** Server Components fetch data without checking membership.
**How to avoid:** Every query must join through classroomMembers/groupMembers to verify the current user has access. Create a reusable `verifyClassroomAccess(classroomId, userId)` and `verifyGroupAccess(groupId, userId)` helper.
**Warning signs:** Able to navigate to `/classroom/[id]` for a classroom you're not a member of.

### Pitfall 3: N+1 Queries on Classroom Dashboard
**What goes wrong:** Fetching classroom, then groups, then member counts, then phases creates cascading queries.
**Why it happens:** Drizzle's `with` is powerful but developers forget to use it.
**How to avoid:** Use Drizzle relational queries with `with` clauses to fetch classroom + groups + member counts in a single query. For the dashboard aggregation (D-03), consider a custom SQL query with `COUNT` and `GROUP BY`.
**Warning signs:** Slow classroom page load, many database roundtrips in server logs.

### Pitfall 4: Invite Code Collision
**What goes wrong:** Two classrooms get the same 6-char invite code.
**Why it happens:** No unique constraint on the invite_code column.
**How to avoid:** Add a unique index on `classrooms.invite_code`. The `generateUniqueInviteCode` function retries on collision, but the DB constraint is the real safety net.
**Warning signs:** Students joining the wrong classroom.

### Pitfall 5: Forgetting Soft Delete in All Queries
**What goes wrong:** Archived phases/todos still appear in the UI.
**Why it happens:** Some queries forget the `isArchived = false` filter.
**How to avoid:** Create helper functions like `getActivePhases(groupId)` and `getActiveTodos(phaseId)` that always include the filter. Never query phases/todos directly without it.
**Warning signs:** Deleted items reappearing.

### Pitfall 6: DnD Provider and Server Components
**What goes wrong:** DragDropProvider errors because it's used in a Server Component.
**Why it happens:** @dnd-kit/react requires client-side React context.
**How to avoid:** The page route file (Server Component) fetches data, then passes it to a `'use client'` component that wraps DragDropProvider. Clear boundary: Server Component = data fetching, Client Component = interactive UI.
**Warning signs:** "createContext is not a function" errors.

### Pitfall 7: Student Auto-Redirect Infinite Loop
**What goes wrong:** Student page redirects to classroom, which redirects back.
**Why it happens:** Redirect logic doesn't account for edge cases (student in classroom but no group yet).
**How to avoid:** Clear redirect chain: (1) student has 0 classrooms -> show empty state, (2) student has 1 classroom -> redirect to classroom, (3) student in classroom but no group -> show "waiting for group assignment" state, (4) student in group -> show phase view.
**Warning signs:** Infinite redirect detected by Next.js, blank page.

### Reorder Action (Atomic)
```typescript
// Source: Drizzle ORM transaction pattern
export async function reorderPhases(groupId: string, orderedIds: string[]) {
  await requireRole(ROLES.TEACHER, ROLES.SUPERADMIN);
  // Verify all phases belong to this group
  const existing = await db.query.phases.findMany({
    where: and(eq(phases.groupId, groupId), eq(phases.isArchived, false)),
  });
  const existingIds = new Set(existing.map((p) => p.id));
  if (!orderedIds.every((id) => existingIds.has(id))) {
    throw new Error('Invalid phase IDs');
  }

  await db.transaction(async (tx) => {
    for (let i = 0; i < orderedIds.length; i++) {
      await tx.update(phases)
        .set({ orderIndex: i, updatedAt: new Date() })
        .where(eq(phases.id, orderedIds[i]));
    }
  });
}
```
