# Quick 261004-02p: Per-group member limit, student roster, student self-grouping Summary

Teachers can now set a member limit per group (falling back to the classroom default), assign, move and remove students from a new "นักเรียน" roster tab, and choose whether students group themselves (`teacher` / `self_join` / `self_create`). Teachers can also edit and delete groups, archived phases, to-dos (one copy or all copies), classrooms and custom templates through one shared Cocoon confirm dialog. Every teacher mutation is now authorized against the classroom it touches.

## What was built

**Data.** The Drizzle schema has two new columns: `groups.max_members` (int, nullable) and `classrooms.group_mode` (text enum, NOT NULL, default `'teacher'`). `src/db/migrations/2026-10-04-group-limits-and-mode.ts` applies them with `ADD COLUMN IF NOT EXISTS`. It is idempotent, runs in one transaction with `lock_timeout 5s` and `statement_timeout 60s`, and asserts that row counts don't change. **I ran it with `--dry-run` only.**

**Rules (pure, unit-tested).**
- `group-rules.ts`: `effectiveGroupLimit`, `isGroupFull`, `limitWarning`, `capacityLabel`, `canStudentJoinGroup`, `canStudentCreateGroup`, `canStudentLeaveGroup`, `checkDeleteConfirmation`, `canDeleteGroup`.
- `classroom-access.ts`: `decideClassroomAccess`.
- `r2-cleanup.ts`: `cleanupR2Objects`.

**Authorization.**
- `assertClassroomEditor` now allows the owner, a classroom teacher member (with global role teacher), or a superadmin. Before, it allowed only the owner or a superadmin.
- New wrappers: `assertGroupEditor`, `assertPhaseEditor`, `assertTodoEditor`.
- Every inline `eq(classrooms.createdBy, …)` check is gone.
- Closed gaps that checked the role only, not the classroom: `updateTodo`, `reorderTodos`, `archiveTodo`, `restoreTodo`, and `removeFromGroup` (which had no ownership check at all).
- `authz-coverage.test.ts` statically checks `classroom/group/phase/todo/template/impact.ts`.

**Server actions.**
- **Groups:** `createGroup` (+maxMembers), `updateGroup` (returns a warning when the new limit is below the member count), `deleteGroup`, `assignStudent`, `moveStudent`, `removeFromGroup`.
- **Student self-grouping:** `joinGroup`, `createGroupAsStudent`, `leaveGroup`.
- **Classroom:** `removeStudent` (also removes their group memberships), `updateClassroomSettings` (+groupMode), `setClassroomArchived`, `deleteClassroom`.
- **Phase / to-do / template:** `deletePhase`, `deleteTodo` (one copy or all copies), `updateTemplate`.
- **Read-only:** `getDeletionImpact`, which supplies the counts shown in confirm dialogs.
- Limit checks run inside transactions that lock the student's `classroom_members` row and the group row (`FOR UPDATE`).
- Delete actions collect R2 keys inside the delete transaction (SELECT before DELETE) and delete the objects best-effort after commit.
- Fixed the plural `revalidatePath` routes.

**Teacher UI.**
- One `ConfirmDialog` for every destructive action, plus an `OverflowMenu` (⋯, 44px hit area).
- "นักเรียน" tab (shown by default when unassigned students exist; `?tab=` overrides):
  - Chips with totals, and search by name/email.
  - Unassigned students: per-row and bulk assign.
  - Assigned students listed by group: move to another group, remove from group, or remove from the classroom.
  - Changes appear immediately and roll back if the server rejects them.
- Group cards show `n/limit คน` and a "เต็ม" pill, with ⋯ เปิด / แก้ไข / ลบกลุ่ม. The group page header has แก้ไขกลุ่ม and ลบกลุ่ม.
- Archived phases have "ลบถาวร". To-dos have "ลบงานนี้" and "ลบงานนี้ในทุกกลุ่ม". Custom templates have แก้ไข / ลบ.
- Settings tab: "การจัดกลุ่ม" radio plus a danger zone (archive/restore, permanent delete). The teacher home puts archived classrooms in a collapsed section.

**Student UI.**
- Teacher mode: a Cocoon waiting card.
- Self modes: a rewritten group picker (join; in `self_create`, also create). Only classmates' names and avatars reach the client.
- In self modes, the group page lets a student leave the group, and lets the `self_create` creator delete it.
- Invite join now lands on `/student/classroom/[id]`.

## Plan-checker watch items

1. **`deleteGroup` does not use a blanket role check.** It calls `authorizeGroupDelete(groupId, userId)` (in phase-helpers), which allows:
   - classroom editors (via `decideClassroomAccess`), or
   - a student who is `group.createdBy` and a student member of the classroom, when the classroom is `self_create` and the group has 0 submissions.

   Anyone else gets an exception. Inside the transaction it locks the group row and re-checks submissions when no confirmation was required. The authz test asserts that `deleteGroup` has no `requireRole(ROLES.TEACHER`.
2. **The decision is a pure helper,** `canDeleteGroup({ isClassroomEditor, isGroupCreator, groupMode, submissionCount })` in `src/lib/group-rules.ts`. Tests cover:
   - teacher allowed without submissions (no confirm needed),
   - teacher allowed with submissions (`requiresConfirmation: true`),
   - self_create creator allowed only at 0 submissions,
   - creator rejected in self_join / teacher mode,
   - non-creator student rejected.
3. **`impact.ts` is in the static scan.** Every export there must call an `assert*Editor` or `authorizeGroupDelete`.
4. **R2 keys are collected inside the delete transaction:** `collectFileKeys(tx, …)` runs right before the DELETE in deleteGroup / deletePhase / deleteTodo / deleteClassroom. `cleanupR2Objects` runs after commit and never throws.

## Deviations from Plan

### Auto-fixed / added

1. **[Rule 2 - Concurrency] Serialize per-student membership changes.** assign / move / join / create-as-student lock the student's `classroom_members` row `FOR UPDATE` before checking "already in a group". Without this, two concurrent calls could put one student in two groups. The group row is also locked for the limit count.
2. **[Rule 2 - Correctness] `deleteGroup` re-checks submissions inside the transaction** when no confirmation was required. If work arrived after the impact check, it asks the user to retry, so a student can't delete a group that just got a submission.
3. **[Rule 2 - Safety] `removeStudent` only removes `student` members.** It returns a Thai error for teacher co-members.
4. **[Rule 1 - Bug] `removeFromGroup` had no ownership check at all.** It now uses `assertGroupEditor`.
5. **[Rule 3 - Testability] `cleanupR2Objects` lives in `src/lib/r2-cleanup.ts`** and is re-exported from phase-helpers. This lets the test import it without Clerk or DB modules.
6. **New small modules:**
   - `src/lib/action-result.ts`: the `ActionResult` type.
   - `src/components/cocoon/use-deletion-impact.ts`: shared impact-fetch hook.
   - `getClassroomGroupMode` in `queries/classroom.ts`: light query for the student group page.
7. **Naming:** the helper parameter is `isGroupCreator`; the watch item's `isSelfCreateCreator` was an example name. The `self_create` requirement is enforced by `groupMode`.
8. **Settings tab:** the old student list removed students with no confirmation. It is now a summary card with avatars and a "จัดการนักเรียน" link to the roster tab, as the plan allowed. There is no second confirm implementation.
9. **Tabs:** the teacher classroom `<Tabs>` is keyed on the explicit `?tab=` value. Redirecting to `?tab=students` after a group delete switches tabs, and refreshing doesn't jump tabs when the unassigned count reaches 0. With four segments, the triggers use tighter padding on mobile.

## Known limitations / deferred

- Tab clicks don't update the URL. So if the teacher is on `?tab=students`, switches to the Groups tab, and deletes a group, they stay on the Groups tab. That's harmless: the group disappears and a toast shows.
- `joinByCode` still **throws** for invalid or already-joined codes, as the plan said to leave it unchanged. In production builds the client toast in `join-code-input` shows a redacted message. The `/join/[code]` server page is not affected. A future fix could return an `ActionResult`.
- `getTeacherClassrooms` still lists only classrooms the teacher **created**. A teacher who is only a `classroom_members` teacher can edit the classroom but won't see it on /teacher. This is unchanged from before and out of scope.
- Deleting submissions/attachments removes R2 objects best-effort. If R2 is not configured, or a delete fails, the objects are orphaned; nothing is retried.
